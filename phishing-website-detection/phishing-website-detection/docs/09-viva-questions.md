# 09 — Viva / Interview Questions

*Thirty questions an examiner is likely to ask, with answers you can defend. The hard ones are at the end.*

---

## A. Understanding the problem

**1. What is phishing, in one sentence?**

A social-engineering attack where a fake page impersonates a trusted site to harvest credentials, delivered by a link the victim is persuaded to click.

**2. Why can't blocklists solve this?**

Blocklists only contain URLs somebody has already reported and verified. The median phishing site lives a few hours, so by the time a URL is listed, the campaign has moved to a new domain. Blocklists are reactive by construction; this system is predictive — it can flag a domain registered ten minutes ago that nobody has ever seen.

**3. Why analyse only the URL and not the page content?**

Three reasons. Speed: ~0.04 ms versus ~200 ms for a network round trip. Safety: you never visit the attacker's server, so you don't leak your IP or risk a drive-by payload. Availability: phishing sites are taken down fast, but the URL stays in inboxes — content analysis returns a 404, lexical analysis still works.

**4. What's the main weakness of that choice?**

A phishing page hosted on a compromised but legitimate domain. `https://realbakery.com/wp-content/uploads/paypal/login.php` has a genuine domain — every hostname feature is useless. Only `brand_outside_domain` fires, from the path. This is a stated limitation, and those cases are deliberately in the dataset so the metrics reflect the weakness.

**5. Is this supervised or unsupervised learning? Why?**

Supervised binary classification. Every training URL has a known label, and the goal is to reproduce that labelling on unseen URLs. Unsupervised methods (clustering, anomaly detection) would be the choice if labels weren't available — a reasonable alternative framing, since phishing is arguably an anomaly-detection problem.

## B. Data

**6. Where does your dataset come from?**

It's generated by `src/dataset.py`: 3,000 legitimate URLs built from 120 real domains, 3,000 phishing URLs built from eight documented attack patterns, plus hard cases. Generated rather than downloaded so the repository clones and runs with no API keys and no dead links — and because committing thousands of live malicious URLs to a public repo would be irresponsible.

**7. Isn't synthetic data a weakness?**

Yes, and the README says so in the headline section. It's a stated trade-off, not a hidden one. Mitigations: the generator reproduces eight patterns documented in the literature; 30% of each class is drawn from deliberately hard generators; and `src/train.py` reads real data from the same CSV path with no code change. The expected drop on a real corpus — to roughly 93–96% — is stated up front.

**8. What are the "hard cases" and why do they matter?**

*(This is the question worth being ready for.)*

The first version of the generator produced clean legitimate URLs versus obviously-bad phishing URLs. **All three models scored exactly 100%** — which proves nothing except that the classes were trivially separable.

So 30% of each class now comes from overlap generators: legitimate bank login pages full of the word "verify", internal dashboards on raw IPs with odd ports, CDN hostnames that look machine-generated; and on the other side, phishing on HTTPS `.com` domains with short clean paths, and phishing kits on hacked legitimate sites.

With hard cases at 0.0 both tree models score exactly 1.0000. At 0.3, Logistic Regression drops to 0.9425 while the tree models stay above 0.99 — and *that 5-point gap is the real finding*: the decision boundary is non-linear.

**9. How do you prevent data leakage?**

Four ways. Deduplication via a `set`, so the same URL can't appear in both train and test. `StandardScaler` inside a `Pipeline`, so scaler statistics are computed from training folds only. The test set is scored exactly once, at the end. Model selection uses cross-validation on the training set, never the test set.

**10. Why 50/50 balance?**

So accuracy is directly interpretable — a coin flip scores 50%, not 90%. Real phishing is heavily imbalanced (a tiny fraction of all URLs), so a production system would need class weights or resampling, and would report precision-recall AUC rather than ROC-AUC.

**11. Why an 80/20 split?**

Standard for a few-thousand-row dataset: enough test data (1,200 rows) for stable metrics, enough training data (4,800) to learn. `stratify=y` preserves the class ratio in both halves.

## C. Features

**12. How many features, and how are they grouped?**

28, in seven groups: size (4), character counts (9), ratios (2), binary red flags (6), content-aware (4), statistical (1), structural (2).

**13. Explain your best feature.**

`brand_outside_domain`. Naively checking "does the URL contain 'paypal'" flags the real PayPal. The insight is that *placement* is what matters: extract the registered domain, then search everything else — subdomain, path, query — for a brand name that isn't in the registered domain.

- `paypal.com/signin` → 0 (brand is the domain: real)
- `paypal.com.evil.tk/login` → 1 (brand is in the subdomain)
- `evil.tk/paypal/verify` → 1 (brand is in the path)

It's the only feature that fires on a phishing kit hosted on a hacked legitimate domain.

**14. What is Shannon entropy and why use it?**

A measure of unpredictability in bits per character: `H = -Σ p(c)·log₂p(c)`. `google.com` scores 2.65 (repeated, predictable letters); `x7q3z9wk2mvb1.tk` scores 3.88 (every character different). Domain Generation Algorithms register random-looking domains in bulk, and this catches them without a blocklist. The confound is that real CDN hostnames are also machine-generated — which is exactly why `_legit_cloud_host` is in the dataset.

**15. Why is `uses_https` a weak feature now?**

It used to be strong. Let's Encrypt made certificates free, and most phishing sites now serve HTTPS. It ranks 4th here with 7% importance — some signal, but far less than a decade-old paper would claim. The padlock proves the connection is encrypted, not that the other end is honest.

**16. Why both `num_digits` and `digit_ratio`?**

`num_digits` confounds with length — a 200-character legitimate URL may contain 20 digits harmlessly. The ratio normalises that. Keeping both lets the model use them jointly: high count *and* high ratio is a stronger signal than either alone.

**17. Your `_registered_domain` is wrong for `bbc.co.uk`. Why ship it?**

*(Have this answer ready — a good examiner will find it.)*

Correct: last-two-labels gives `co.uk` as the registered domain for `www.bbc.co.uk`. The right fix is the Public Suffix List via `tldextract`. It's not used because it would add a dependency to a project that otherwise runs on scikit-learn alone. The error is *consistent* — it applies identically to both classes, so it doesn't bias the classifier — and affects roughly 8% of domains. It's documented in doc 03 §3.4 and listed as the first thing to fix before using real data.

**18. Why not TF-IDF on character n-grams?**

It's a genuinely competitive alternative, and published work shows it performs comparably. Rejected for explainability: TF-IDF gives 50,000 anonymous n-gram weights, so you can't tell a user *why* a URL was flagged, and per-prediction explanation was a stated requirement. Also, importances over 28 named features teach you something about phishing; importances over 50,000 n-grams teach you nothing. It's listed as a comparison worth running.

## D. Modelling

**19. Which models, and why those three?**

Logistic Regression (linear baseline), Random Forest (bagging), Gradient Boosting (boosting). They span a deliberate range of capacity. Including a linear baseline answers the question "is the complexity actually buying anything?" — which turned out to be the most interesting result in the project.

**20. Difference between Random Forest and Gradient Boosting?**

Random Forest trains many deep trees **independently** on bootstrap samples and averages them — it reduces **variance**. Gradient Boosting trains shallow trees **sequentially**, each fitted to the previous ensemble's residual errors — it reduces **bias**. Parallel and independent versus sequential and corrective.

**21. Why is Logistic Regression 5 points worse?**

Because the boundary is non-linear. A linear model learns one fixed weight per feature: "more entropy → more phishing". It cannot express *conditional* rules like "high entropy means phishing **unless** the TLD is `.net` and the path starts with `/assets/`, in which case it's a CDN". Trees express that with two nested splits. Every hard case in the dataset needs that kind of conditional.

**22. Why is Gradient Boosting your winner over Random Forest?**

Strictly, it shouldn't be called a winner. Test F1 is 0.9925 vs 0.9908 — two URLs out of 1,200, with overlapping CV intervals (0.9925 ± 0.0014 vs 0.9917 ± 0.0028). Rerun with dataset seed 99 and Random Forest wins instead. They're statistically indistinguishable; the script picks Gradient Boosting only because the tie-break rule is test F1. The defensible claim is that **both tree ensembles beat the linear baseline, consistently, at every seed**.

**23. Why F1 and not accuracy?**

Accuracy is fine on a balanced dataset but breaks on imbalanced data — and real phishing data is imbalanced. F1 is the harmonic mean of precision and recall, so it punishes a model that sacrifices one for the other. In production you'd weight recall higher than precision (F2), because missing phishing costs more than a false alarm.

**24. Why is `StandardScaler` inside the Pipeline rather than applied first?**

To prevent leakage. Scaling the whole dataset before splitting lets the test set's mean and standard deviation influence the training data. Inside a Pipeline, `fit()` computes those statistics from the training fold only — and this happens correctly in every cross-validation fold automatically.

**25. What does 5-fold cross-validation tell you that the test score doesn't?**

Stability. A single test score could be a lucky split. CV mean ± σ across five different partitions shows whether the result holds. Here σ ≤ 0.003 for all three models, so they're stable. CV is also slightly pessimistic (each fold trains on 80% of the training data), so a test score far above CV would be a warning sign.

## E. Results and limitations

**26. Walk me through a URL your model got wrong.**

*(Know both. This question separates people who ran a script from people who understand their system.)*

There were nine errors: 6 missed phishing, 3 false alarms.

**False negative:** `https://oovdlhtk.web.app/`, scored 0.163. HTTPS, 25 characters, `.app` is a normal Google TLD, no path, no brand name, zero urgency words. Every feature says legitimate. Nothing in the string is actually wrong — this is the fundamental limit of lexical analysis. Catching it needs domain age or page content.

**False positive — and this is the more interesting one:** `https://stackoverflow.com/`, scored 0.948. An ordinary top-tier website with nothing wrong with it at all.

The cause is a flaw in my own dataset, not in the model. Among legitimate URLs only 2 of 29 path templates produce a bare domain, while two of the phishing generators produce bare domains by design. So the model learned "HTTPS + bare domain + no path → phishing" — a rule that is true in my data and false in the world.

I left it in and documented it rather than quietly patching the generator, because it demonstrates something worth demonstrating: a model will happily learn a spurious correlation, and at 99.25% accuracy the flaw is completely invisible in the headline number. The only way to catch it is to look at individual errors.

**27. Your top feature carries 40% of the decision. Is that a problem?**

Yes, and it's worth naming. Partly it's real — phishing URLs are genuinely stuffed with urgency words. But partly it's an artifact: the generator draws phishing paths from a fixed `PHISH_WORDS` pool, making the signal cleaner than reality. On a real corpus the feature would stay important but wouldn't dominate at 40%.

More generally, any single feature carrying 40% in a 28-feature model is a signal to go looking for a data artifact — which is exactly how I found the bare-domain problem in Q26.

**28. How would this perform on real data?**

Worse, and that's expected. Realistically 93–96% accuracy with these features on PhishTank + Tranco. The drop comes from the two failure modes above, which are rare in the generator and common in the wild. Anyone reporting 99% on real phishing data has probably leaked test data into training.

**29. What would you do next, with a month?**

In priority order: (1) evaluate on real PhishTank + Tranco data — the single biggest credibility gain; (2) add a domain-reputation feature, which fixes the false positive directly; (3) swap in `tldextract` for correct suffix parsing; (4) add SHAP for true per-prediction explanations instead of the current rule layer; (5) build the browser extension, since detection without delivery helps nobody.

**30. Is this production-ready?**

No, and the docs say so. It runs on Flask's development server (single-threaded, explicitly not for production), has no rate limiting, no model versioning, no monitoring for concept drift, and no retraining schedule. Phishing patterns shift monthly, so a deployed version would need weekly retraining and drift alerts. It's a research and coursework system that demonstrates the approach works.

---

## Three things to have at your fingertips

**The number:** 99.25% accuracy, F1 0.9925, on 1,200 held-out synthetic URLs — and immediately, unprompted, "that's synthetic data; expect 93–96% on a real corpus."

**The insight:** the 5-point gap between Logistic Regression and the tree ensembles proves the decision boundary is non-linear, and that gap only appears once hard cases are in the dataset. Without them the tree models score exactly 100% and you learn nothing.

**The limitation:** two of them, actually. A phishing page on a hacked legitimate domain is close to invisible to lexical features, because nothing in the URL is wrong. And my own dataset taught the model a spurious rule about bare domains, which I found by reading the errors rather than the score.

Volunteering the limitation before being asked reads as rigour. Being caught not knowing it reads as having run someone else's script.
